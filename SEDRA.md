# Sedra on rusty-kaspa

This repository is a Sedra node built on [rusty-kaspa](https://github.com/kaspanet/rusty-kaspa) **v1.0.1**
(`fcd9c28f`), the Rust node of Kaspa. Sedra's own node, `sedrad`, is a copy of Kaspa's Go node v0.12.15; this project
moves Sedra to the Rust codebase. It is part of the
[Sedra merged-mining project](https://github.com/necatgit/sedra-merged-mining); the reasoning is in its
`research/0004-rust-path.md`.

**Status: work in progress. Not for mainnet use.**

## Branches

- `main`: unmodified upstream rusty-kaspa v1.0.1, as a reference point.
- `dev`: Sedra changes. Every change is listed below.

## Goal of Step 1

A node with exactly the same consensus rules as Sedra mainnet today (sedrad v2.0.0, `4a1153d`), able to sync and run
next to the existing Go nodes. No fork. Progress is tracked as milestones M1-M9 in the project repository.

## Step 2: merged mining (branch `m10-auxpow`, not in `dev`)

Work towards SIP-0001. Nothing of it is active; it lives only on this branch until the proposal is agreed.

**Kaspa parents (M10 step 1).** `consensus/core/src/kaspa_parent.rs`. Kaspa's header hash is unchanged since
v1.0.1 (version 2 headers compress the parents only for storage; the hash runs over the expanded parents), so a Kaspa
parent header is a normal `Header` with expanded parents. Kaspa's coinbase, however, is a **version 1** transaction
since Toccata (outputs carry a covenant flag, the mass is always committed), which this code base cannot represent,
so it has its own type `KaspaParentCoinbase` with Kaspa's current hashing; an unknown future version is not hashed
(merged mining pauses, native mining continues). `merkle_root_from_coinbase` folds the coinbase's Merkle branch.
Tests in `consensus/src/processes/sedra_auxpow_parent_test.rs` against 20 consecutive real Kaspa mainnet blocks
(`testing/integration/testdata/kaspa_mainnet_headers_v2.json.gz` from a Kaspa node's GetBlock,
`kaspa_mainnet_coinbases_v1.json.gz` from api.kaspa.org): 20/20 header hashes and kHeavyHash checks, 20/20 coinbase
hashes equal Kaspa's, 20/20 branches reach `hashMerkleRoot` (depths 0 to 3), plus negative cases. Removing the
mass field, the covenant flag or the lock time from the hash, or accepting a future version, makes them fail.

**The proof (M10 step 2).** `consensus/core/src/auxpow.rs`: `AuxPow` = Kaspa parent header + `KaspaParentCoinbase` +
Merkle branch, Borsh-serializable, outside the Sedra header hash. Structural rules of SIP-0001 §4.1-§4.5 in
`verify_binding`: branch at most 64 entries, proof at most 256 KiB, hashable coinbase, exactly one `SDM1` tag followed
by the canonical base64url (no padding) encoding of `H("sedra_aux_bind1" || genesis || nonce-free header hash)`
(block-hash hasher), the coinbase under the parent's `hash_merkle_root`, and the Sedra nonce equal to the first 8 bytes
(LE) of the recomputed parent hash. `payload_carries_commitment` is the input for the self-parent ban (§4.5). Each
failure has its own `AuxPowError`. Tests: commitment and base64url against values computed independently in Python,
the tag rules, and a full proof built on a real Kaspa block with every single rule broken once; removing any of six
rules (second tag, nonce, genesis, canonical encoding, branch limit, Merkle check) fails them. Not yet: the parent's
work check against the Sedra target, the activation point, P2P/RPC transport (next steps).

**The work check (M10 step 3).** `consensus/pow/src/auxpow.rs`: `verify_aux_pow` runs the binding checks, then the
Kaspa parent's kHeavyHash against the **Sedra** target from the Sedra header's `bits` (the parent's own `bits` are not
checked, §4.4). `check_pow_gated` is the dual-acceptance gate: native first, so a missing or bad proof never
invalidates a natively valid block; the proof path only after activation (`AuxRule`). `calc_block_level_check_pow_gated`
takes an aux block's level from the parent's work (§4.7); pruning-proof validation must use it with the same rule.
Tests on a real Kaspa parent mined against a test target: accepted, insufficient work, wrong network, gate off,
native first with a bad proof, block level. Removing any of six rules (work check, Sedra instead of parent target,
native first, gate, level from the parent, binding) fails them. Not yet wired into the header pipeline (step 4).

**The header field (M10 step 4a).** `Header::aux_pow: Option<Box<AuxPow>>`, outside the header hash, so the block hash
does not depend on how the block was mined and a peer can strip the proof without changing the block's identity. A
proof whose parent carries a proof is rejected (`NestedProof`). The header's memory estimate counts the proof. The header
store format changed, so the DB version is now **5**: an older Rust-node database is deleted after confirmation (or
`--yes`) and the node resyncs; the old 3-to-4 soft upgrade no longer applies.

**Transport (M10 step 4b).** P2P: `BlockHeader.auxPow` (bytes, field 15 as in ZKas; older nodes ignore it). An unusable
proof from a peer (too large, undecodable, nested, branch too long) is dropped and the header kept, so a relay cannot
kill a natively valid block or a sync batch; a block that needed the proof then fails PoW, which is not cached as
invalid. RPC: the mining header `RpcRawHeader.auxPow` (hex, gRPC field 16 as in ZKas, wRPC format 2 with format 1 still
accepted, JSON may omit it) so a pool submits a merged-mined block through the normal `submitBlock`; a bad proof there is
an error the pool sees. The query header (`getBlock`) carries no proof, as in ZKas.

**Activation and wiring (M10 step 4c).** `Params::aux_pow_activation` (DAA score; `never` on every network until the
score is agreed with the Sedra team after a public testnet). Header validation runs `check_pow_gated` with the header's
claimed DAA score; pruning-proof build, apply and validate derive levels through the same gate (§4.7). Self-parent ban
(§4.5): from `coinbase_commitment_ban_activation()` = activation minus `2 * finality_depth` (about 2 days on mainnet,
decided 2026-11-10 as in ZKas) a coinbase with an `SDM1` commitment is invalid
(`CoinbaseCarriesMergeMiningCommitment`), so Go nodes must be replaced before the ban starts, not at activation.
Consensus tests on simnet with real PoW: a stripped proof fails PoW without blacklisting the block and the same block
with the proof is accepted (the header store keeps it); a proof for another block fails; before activation the proof
is ignored and the ban is off; the ban rejects a natively valid block after its start; pruning-proof levels follow the
parent's work after activation only.

**Fuzzing and two-node test (M10 step 5a/5b).** Deterministic fuzz tests (no new dependencies) drive mutated and
random proofs through the decoder, the structural and binding checks, the PoW gate and the P2P and RPC conversions: no
panic, P2P never rejects a header, RPC answers ok or error. The only freedom fuzzing found is the parent header cached
hash field, which no rule reads; both decode edges now replace it with the recomputed hash.
`testing/integration` `sedra_auxpow_sync_tests`: node A (simnet, real PoW, small pruning depths) mines 240 valid blocks, every second one
merged-mined; node B accepts all of them through the P2P header conversion; a fresh node validates A's pruning proof
(319 merged-mined headers in 9 levels); a node without merged mining rejects the merged-mined block and the proof
(`PruningProofWrongBlockLevel`, the ZKas sync bug class).

## Releases

`sedra_release()` in `core/src/kaspad_env.rs` holds the release of this node (`0.1.0` for step 1). `kaspad --version`
and the startup log show it with the upstream base and the commit, e.g. `0.1.0 (rusty-kaspa v1.0.1, commit
9cb74efc1234)`. The P2P user agent stays the upstream `kaspad:1.0.1`, so the handshake with the Go nodes is unchanged.

Releases are built reproducibly (`contrib/reproducible/`, pinned Rust image and Debian snapshot; `rust-toolchain.toml` pins
rustc 1.99.1) and verified by rebuilding: see `docs/RELEASE.md`. The upstream release workflow
(`.github/workflows/deploy.yaml`) is removed: it built unverifiable binaries under Kaspa's names on every GitHub release.
The upstream README is kept as `docs/README-rusty-kaspa.md`. `utils/build.rs` also embeds the commit when HEAD is detached (a checked-out release tag); upstream embedded none in that case.

## Building

On Linux with Rust (rustup), clang, protoc, cmake and the usual build tools
(`build-essential clang llvm libclang-dev pkg-config libssl-dev protobuf-compiler cmake`):

```
cargo build --release --bin kaspad
cargo test --release --no-fail-fast --workspace --exclude kaspa-wasm --exclude kaspa-wallet-pskt
```

Tested on Ubuntu 24.04 (GCC 13) and Ubuntu 26.04 (GCC 15), both with rustc 1.99.1.

**GCC 15 note:** RocksDB 8.10, which this version uses, does not include `<cstdint>` itself and fails to compile with
GCC 15. `.cargo/config.toml` adds `-include cstdint` to `CXXFLAGS` automatically. If you set your own `CXXFLAGS`,
include `-include cstdint` in it.
